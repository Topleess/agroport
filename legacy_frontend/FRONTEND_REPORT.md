# Отчет по фронтенду приложения «Агропорт»

## 1. Краткое резюме

«Агропорт» сейчас реализован как фронтенд-прототип цифровой платформы для малого агробизнеса: фермер видит меры поддержки, финансовые и экспортные программы, витрину товаров, кооперационные запросы, обучение, мероприятия и личный кабинет хозяйства.

Технически приложение построено на Next.js `16.2.6` с App Router, React `19.2.4`, TypeScript и Tailwind CSS `4`. Backend/API слоя в текущей реализации нет: все данные импортируются из `src/lib/mock-data.ts`, а обработка выполняется прямо в компонентах через локальное состояние, фильтрацию массивов и навигацию Next.js.

Текущий фронт хорошо подходит как интерактивный UI-прототип и основа для MVP. Для продуктовой версии нужно добавить слой данных, авторизацию, реальные формы, валидацию, состояния загрузки/ошибок и серверную обработку заявок, товаров, документов и профиля.

## 2. Технологический стек

| Область | Реализация | Комментарий |
| --- | --- | --- |
| Framework | Next.js `16.2.6` | Используется App Router в `src/app`. |
| UI runtime | React `19.2.4` | Компоненты разделены на Server Components и Client Components. |
| Язык | TypeScript | Включен `strict: true` в `tsconfig.json`. |
| Стили | Tailwind CSS `4` | Utility-first стили прямо в JSX, глобальные настройки в `src/app/globals.css`. |
| Иконки | `lucide-react` | Используются для навигации, карточек, статусов и действий. |

| Backend/API | Отсутствует | Нет `fetch`, `route.ts`, Server Actions, cookies/session/auth. |

### 3.2. Server Components и Client Components

По правилам Next.js App Router страницы являются Server Components по умолчанию. Это используется на большинстве статичных страниц, где достаточно импортировать mock-данные и отрендерить JSX.

Client Components используются там, где нужна интерактивность:

| Файл | Причина `"use client"` |
| --- | --- |
| `src/components/platform-shell.tsx` | Использует `usePathname` для подсветки активного пункта меню. |
| `src/components/onboarding-modal.tsx` | Использует `useState` и `useMemo` для пошаговой анкеты. |
| `src/components/listing-modal.tsx` | Использует обработчики `onClick` для закрытия модального окна. |
| `src/app/support/page.tsx` | Использует `useState` и `useMemo` для фильтрации каталога. |
| `src/app/marketplace/page.tsx` | Использует `useState` для открытия модалки товара/запроса. |
| `src/app/profile/products/page.tsx` | Использует `useState` для открытия модалки добавления товара. |
| `src/app/profile/requests/page.tsx` | Использует `useState` для открытия модалки добавления запроса. |

### 3.3. Особенности Next.js 16

В проекте уже учтено актуальное поведение Next.js 16: `params` и `searchParams` в `page.tsx` используются как `Promise`.

Примеры из текущего кода:

```tsx
export default async function SupportDetailPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;
}
```

```tsx
export default async function ProfilePage({
  searchParams,
}: {
  searchParams: Promise<{ onboarding?: string }>;
}) {
  const { onboarding } = await searchParams;
}
```

Это соответствует локальной документации Next.js в `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/page.md`: `params` и `searchParams` являются promise-значениями и должны читаться через `await` или React `use`.

## 5. Обработка данных и состояния

### 5.1. Data flow

Сейчас поток данных максимально простой:

1. Данные объявлены в `src/lib/mock-data.ts`.
2. Страница или компонент импортирует нужный массив/объект.
3. JSX рендерит данные через `.map(...)`, `.slice(...)`, `.find(...)` и простые вычисления.
4. Никакого сохранения в backend, storage или URL query для фильтров нет.

Примеры источников данных:

| Данные | Использование |
| --- | --- |
| `farmerProfile` | Профиль, header кабинета, рекомендации по заполнению. |
| `topNav` | Главное меню в header. |
| `profileMenu` | Боковое меню кабинета. |
| `supportMeasures` | Каталог поддержки и detail-страницы `/support/[id]`. |
| `financePrograms` | Финансовый каталог и detail-страницы `/finance/[id]`. |
| `exportPrograms` | Экспортный каталог и detail-страницы `/export/[id]`. |
| `marketplaceItems` | Витрина и товары в кабинете. |
| `cooperationRequests` | Кооперация и запросы в кабинете. |
| `applications` | Заявки в кабинете. |
| `learningItems` | Обучение. |
| `events` | Мероприятия. |
| `serviceTiles` | Сервисы хозяйства. |

### 5.2. Client state

Локальное состояние используется точечно.

В `/support`:

```tsx
const [category, setCategory] = useState("Все");
const [query, setQuery] = useState("");
```

`useMemo` вычисляет видимый список:

```tsx
const visible = useMemo(() => {
  return supportMeasures.filter((item) => {
    const categoryMatch = category === "Все" || item.category === category;
    const queryMatch = `${item.title} ${item.goal} ${item.organizer}`
      .toLowerCase()
      .includes(query.toLowerCase());
    return categoryMatch && queryMatch;
  });
}, [category, query]);
```

В `OnboardingModal`:

| State | Назначение |
| --- | --- |
| `step` | Текущий шаг анкеты от `0` до `4`. |
| `type` | Выбранный тип хозяйства. |

`useMemo` используется для заголовка текущего шага, который зависит от `step` и `type`.

В `MarketplacePage`, `ProfileProductsPage`, `ProfileRequestsPage` состояние управляет открытием модального окна:

| Экран | State |
| --- | --- |
| `/marketplace` | `modal: "product" | "request" | null` |
| `/profile/products` | `modalOpen: boolean` |
| `/profile/requests` | `modalOpen: boolean` |

### 5.3. Routing

Навигация реализована через `next/link`. Это основной механизм переходов между страницами, detail-экранами и кабинетом.

Активное состояние меню вычисляется через `usePathname`:

| Место | Логика |
| --- | --- |
| Header | Для публичного верхнего меню активен пункт, чей `href` совпадает с текущим путем или является его началом. |
| CabinetShell | Для меню кабинета активен пункт, чей `href` полностью равен текущему пути. |

Динамические страницы используют `[id]`:

| Route | Источник данных | Поведение при неизвестном id |
| --- | --- | --- |
| `/support/[id]` | `supportMeasures.find(...)` | `notFound()` |
| `/finance/[id]` | `financePrograms.find(...)` | `notFound()` |
| `/export/[id]` | `exportPrograms.find(...)` | `notFound()` |

### 5.4. Forms and actions

Формы сейчас визуальные. Поля ввода не связаны с постоянным хранилищем, не отправляются на сервер и не валидируются.

Примеры:

| Экран/компонент | Текущее поведение |
| --- | --- |
| `/login` | Поля email/password визуальные, кнопка ведет в `/profile?onboarding=1`. |
| `/register` | Поля регистрации визуальные, кнопка ведет в `/profile?onboarding=1`. |
| `OnboardingModal` | Переключает шаги локально, не сохраняет анкету. |
| `ListingModal` | Поля товара/запроса визуальные, кнопки закрывают модалку. |
| Detail-страницы | Кнопки вроде «Начать заявку», «Проверить профиль», «Рассчитать заявку» пока не выполняют бизнес-действий. |

Это важно учитывать при доработке: UI уже показывает будущие сценарии, но под ними пока нет прикладной логики.

## 6. Визуальная система и UX

Приложение использует карточную композицию с большим количеством скруглений, светлыми поверхностями и зеленым/бирюзовым/голубым акцентом.

Основные приемы:

| Прием | Где встречается |
| --- | --- |
| Белые карточки с border | Каталоги, detail-блоки, FAQ, кабинет. |
| Зеленые/бирюзовые CTA | Основные действия: найти субсидию, добавить, продолжить. |
| Голубые CTA | Detail-переходы, открыть детали, рассчитать заявку. |
| Градиентный фон | Кабинет и detail-страницы через `CabinetShell` и `DetailShell`. |
| Иконки `lucide-react` | Меню, карточки, статусы, контакты, действия. |
| Крупные заголовки | Лендинг, каталоги и detail-страницы. |

Глобальные стили находятся в `src/app/globals.css`. Шрифты Geist подключены в `src/app/layout.tsx` через `next/font/google`.

Текущие UX-ограничения:

- Кнопка мобильного меню в header отображается, но не открывает меню.
- Модальные окна не имеют полноценного focus trap и закрытия по Escape.
- На некоторых кнопках есть будущие действия без обработчиков.
- Фильтры витрины визуально показаны, но фактически не фильтруют список.
- Поиск в витрине визуальный, но не привязан к состоянию.

## 7. Текущие ограничения прототипа

| Ограничение | Что это значит для разработки |
| --- | --- |
| Нет backend/API | Нельзя реально сохранять профиль, заявки, товары, документы и обращения. |
| Нет авторизации | `/login` и `/register` только имитируют вход. |
| Нет data-access слоя | UI напрямую импортирует mock-данные; замена на API потребует правок во многих местах. |
| Нет Server Actions / Route Handlers | Формы не имеют серверной обработки. |
| Нет persistent state | После действий данные не меняются и не сохраняются. |
| Нет loading/error/empty состояний | При переходе на реальные API их придется добавить. |
| Нет тестов | Поведение фильтров, маршрутов и модалок не закреплено автотестами. |
| Нет доступных модалок полного уровня | Нужно доработать `aria`, focus management и keyboard behavior. |

## 8. Рекомендации по доработке

### 8.1. Быстрый MVP

Для быстрого MVP лучше не переписывать UI, а аккуратно добавить слой данных между страницами и текущими mock-данными.

Рекомендуемые шаги:

1. Описать доменные типы отдельно от mock-массивов: `FarmerProfile`, `SupportMeasure`, `FinanceProgram`, `ExportProgram`, `MarketplaceItem`, `CooperationRequest`, `Application`.
2. Создать data-access модуль, например `src/lib/data/`, с функциями:
   - `getFarmerProfile()`
   - `getSupportMeasures()`
   - `getSupportMeasureById(id)`
   - `getFinancePrograms()`
   - `getFinanceProgramById(id)`
   - `getExportPrograms()`
   - `getExportProgramById(id)`
   - `getMarketplaceItems()`
   - `getCooperationRequests()`
3. На первом этапе эти функции могут возвращать данные из `mock-data.ts`.
4. Страницы должны обращаться к data-access функциям, а не напрямую к массивам.
5. После этого mock-данные можно заменить на API или БД без полной переработки UI.

Этот путь самый безопасный: он сохраняет текущий внешний вид и маршруты, но готовит приложение к настоящим данным.

### 8.2. Продуктовая версия

Для продуктовой версии нужно добавить настоящую прикладную логику:

- Авторизация и сессия пользователя.
- Реальный профиль хозяйства с сохранением прогресса заполнения.
- CRUD для товаров и запросов.
- Заявки на меры поддержки и финансовые программы.
- Документы и статусы проверки.
- Обращения в поддержку.
- Роли или типы пользователей, если будут фермеры, консультанты, администраторы.
- Валидация форм на клиенте и сервере.
- Loading, error и empty состояния на всех списках.

Архитектурно лучше двигаться от текущего UI к backend через тонкий BFF/data-access слой, а не подключать API прямо внутри каждого компонента.

### 8.3. Качество и поддерживаемость

Что стоит улучшить после появления реальных сценариев:

- Добавить e2e smoke-тесты на основные маршруты: `/`, `/support`, `/support/farmer-grant`, `/marketplace`, `/profile`.
- Добавить тест фильтрации каталога `/support`.
- Проверить доступность модалок: `aria-labelledby`, focus trap, закрытие по Escape, возврат фокуса.
- Сделать мобильное меню в header рабочим.
- Унифицировать дизайн-токены цветов, радиусов и shadow, чтобы не размножать inline Tailwind-значения.
- Добавить пустые состояния для списков: нет мер, нет товаров, нет заявок, нет результатов поиска.
- Разделить сложные страницы на более мелкие секции, если они начнут расти вместе с бизнес-логикой.

## 9. Предлагаемый порядок реализации следующих работ

Оптимальный порядок доработки:

1. Зафиксировать доменные типы и data-access слой поверх текущих mock-данных.
2. Перевести страницы каталогов и detail-страницы на data-access функции.
3. Добавить рабочие формы для onboarding и товаров сначала на локальном/mock persistence уровне.
4. Подключить авторизацию и профиль пользователя.
5. Заменить mock persistence на backend/API.
6. Добавить loading/error/empty состояния.
7. Покрыть основные маршруты smoke-тестами.
8. Доработать accessibility модалок и мобильную навигацию.

## 11. Итоговая оценка

Текущий фронтенд хорошо собран как демонстрационный прототип: есть понятная карта разделов, единая визуальная оболочка, личный кабинет, detail-страницы, фильтрация мер поддержки и модальные сценарии добавления. Код достаточно компактный, поэтому его удобно развивать.

Главный технический риск сейчас не в UI, а в отсутствии слоя данных. Если сразу начать подключать API точечно в разные страницы, приложение быстро станет сложнее поддерживать. Лучший следующий шаг - добавить typed data-access слой и постепенно заменить прямые импорты из `mock-data.ts` на функции получения данных. Это даст аккуратный мост от прототипа к MVP без потери уже сделанного интерфейса.
